# Microservices Distributed Transactions & Atomicity Guarantee

---

## 🎯 一、核心痛点：为什么微服务不能直接用单体 ACID？

在单体架构中，所有业务共享同一个数据库，依靠关系型数据库底层的 **ACID 机制**（`Undo Log` 回滚、`Redo Log` 持久化、`排他锁/MVCC` 隔离）即可天然保证原子性。

拆分为微服务后，**数据库物理隔离且跨网络调用**：

- 无法在网络连接之间传递数据库级别的排他锁；
- 遵从 **CAP 定理** 与 **BASE 理论**（Basically Available 基本可用，Soft state 软状态，Eventually consistent 最终一致性）；
- **核心转变：放弃强阻塞的单体 ACID 事务，转向"最终一致性"或"应用层两阶段提交"。**

## 🏗️ 二、三大主流分布式事务方案详解

```text
               ┌─────────────────────────────────────────┐
               │        微服务分布式事务（原子性保障）      │
               └────────────────────┬────────────────────┘
                                    │
     ┌──────────────────────────────┼──────────────────────────────┐
     ▼                              ▼                              ▼
【1. 事务消息 / 本地消息表】     【2. Saga 模式】              【3. TCC 模式】
(Outbox Pattern，异步最终一致)  (正向操作 + 逆向补偿)          (Try - Confirm - Cancel)
```

### 方案 1：事务消息 / 本地消息表（Outbox Pattern）

**一句话总结**：利用"本地数据库 ACID 事务"绑定"业务变更"与"消息写入"，再依靠 MQ 实现下游服务的最终一致性。

**运行机制：**

- **上游服务（如订单服务）**：在本地 DB 开启事务：插入订单数据，顺便向 `t_outbox`（本地消息表）插入待发送消息，提交本地事务（保证订单生成与消息存盘 100% 同成功或同失败）。
- **异步投递**：通过 CDC（如 Debezium / Canal）或定时任务拉取 `t_outbox` 数据，投递到 MQ（Kafka / RocketMQ）。
- **下游服务（如积分服务）**：监听 MQ 消息，并在本地开启事务消费，更新积分。
- **兜底保障**：下游服务做**强幂等校验**；若消费失败，利用 MQ 重试机制或死信队列（DLQ）触发人工/脚本补单。

**适用场景**：跨服务异步调用（如：下单 → 发积分、下单 → 发短信）。

### 方案 2：Saga 模式（正向操作 + 逆向补偿）

**一句话总结**：将长业务流程拆分为一串按顺序执行的本地小事务；一旦某一步失败，逆向依次调用各个服务的"补偿接口"进行数据回滚。

**运行机制：**

- **正向链路（T）**：服务 A (T₁) → 服务 B (T₂) → 服务 C (T₃ 失败！)。
- **逆向补偿链路（C）**：触发 Saga 协调器，依次反向调用：服务 B 的补偿接口 C₂（返还库存）→ 服务 A 的补偿接口 C₁（取消订单）。

```text
【正常流程】  [ T1: 创建订单 ] ──> [ T2: 扣减库存 ] ──> [ T3: 扣除余额 ]
                                                            │
【异常回滚】  [ C1: 废弃订单 ] <── [ C2: 返还库存 ] <────────┘ (T3 失败)
```

**两种恢复策略：**

- **向后恢复（Backward Recovery）**：正向步骤 Tₖ 失败，回滚已完成的所有步骤（依次执行 Cₖ₋₁, …, C₁）。适合大多数业务（如：创建订单失败，取消并退还预留的优惠券）。
- **向前恢复（Forward Recovery）**：正向步骤 Tₖ 失败，不进行回滚，不断重试 Tₖ 直至成功。适合必须成功的业务（如：扣款已成功后的发短信/生成电子发票，不能因为短信失败就退款）。

### 方案 3：TCC 模式（Try - Confirm - Cancel）

**一句话总结**：在应用代码层实现的强一致性两阶段提交（2PC），通过"资源预留/冻结"规避全局锁。

**🛠️ 运行机制（以"转账扣款 100 元"为例）：**

| 阶段 | 核心动作 | 物理表层面的 SQL 落地 |
| --- | --- | --- |
| **1. Try**（预留资源） | 检查业务合法性，预留/冻结资源 | `UPDATE t_account SET balance = balance - 100, frozen_amount = frozen_amount + 100 WHERE user_id = 101 AND balance >= 100;` |
| **2. Confirm**（真正提交） | 若所有服务 Try 均成功，使用预留资源完成业务 | `UPDATE t_account SET frozen_amount = frozen_amount - 100 WHERE user_id = 101 AND frozen_amount >= 100;` |
| **3. Cancel**（释放资源） | 若任意服务 Try 失败，解冻并释放预留资源 | `UPDATE t_account SET balance = balance + 100, frozen_amount = frozen_amount - 100 WHERE user_id = 101 AND frozen_amount >= 100;` |

**⚠️ TCC 落地三大避坑点：**

- **空回滚（Empty Cancel）**：因网络超时导致 Try 未送达，但 TCC 协调器直接发起了 Cancel。*解法*：Cancel 先查本地日志，若无 Try 记录直接返回成功。
- **防悬挂（Anti-Suspension）**：拥堵的 Try 请求在 Cancel 执行完毕后才迟到，导致资金永久被冻结。*解法*：Try 执行前检查是否已有 Cancel 记录，若有则拒绝执行。
- **强幂等性（Idempotency）**：避免网络超时重试导致 Confirm 或 Cancel 被重复执行多次。

## ⚡ 三、核心深度：若阶段 C (Confirm/Cancel/Compensate) 执行失败怎么办？

> **核心哲学**：无论是 TCC 的 Confirm/Cancel 还是 Saga 的 Compensate，业务逻辑合法性均已在第一阶段验证完毕。因此第二阶段 C 的操作在逻辑上【只许成功，不许失败】！若失败 100% 为网络/宕机等物理异常。

```text
[ 二阶段 C 执行失败 (如网络中断/数据库死锁/服务宕机) ]
                         │
                         ▼
  【 第一防线：事务协调器后台无限重试 】 ──(重试成功)──> [ 事务最终完成 ]
                         │ (指数退避重试 N 次依旧失败)
                         ▼
  【 第二防线：C 接口强幂等保障 】 ──────(防止重试导致数据二次扣减/解冻)
                         │
                         ▼
  【 第三防线：事务日志 (Log) 断点续传 】 ─(编排器宕机重启后顺着 Log 继续补偿)
                         │
                         ▼
  【 第四防线：死信高警 + 人工干预 】 ────(标记为脏事务，由补单脚本/人工介入修正)
```

- **协调器自动重试（Retry）**：TCC/Saga 协调器根据持久化的事务日志，通过后台线程采取指数退避算法无限次重试调用失败的 C 接口，直到服务恢复并返回成功。
- **C 接口强幂等**：为配合重试，C 接口内部必须通过状态表或业务字段进行幂等校验。
- **日志断点续传**：协调器本身宕机重启后，读取数据库里的事务状态日志（Transaction Log），继续对未完成的事务执行二阶段 C 操作。
- **人工兜底（Manual Intervention）**：若因代码 Bug 等不可恢复异常导致重试超限，事务标记为 DIRTY 并触发告警，由运维通过补单脚本纠偏。

## 🥊 四、终极碰撞：Saga 与 TCC 的本质区别是什么？

很多人误以为两者区别只是"有没有 Try 阶段"，其实本质区别在于【资源隔离性】与【中间状态可见性】：

```text
【 TCC 模式 (预授权) 】
[ Try 阶段 ] ──> 修改冻结字段 (frozen_amount +100) ──> 资源被锁定隔离，外部不可见
[ Confirm  ] ──> 真正扣除 (frozen_amount -100)

【 Saga 模式 (全款后退款) 】
[  T 阶段  ] ──> 直接真实扣除 (balance -100) 并直接 COMMIT ──> 外部立刻可见(存在脏读风险)!
[  C 阶段  ] ──> 逆向加回 (balance +100) 并重新 COMMIT
```

| 比较维度 | TCC 模式 | Saga 模式 |
| --- | --- | --- |
| **通俗比喻** | 信用卡预授权（冻结额度） | 直接全款扣钱，不行再退款 |
| **隔离性 (Isolation)** | 🟢 高（资源被 Try 冻结，外部无法并发抢占） | 🔴 无（T 阶段已提交存盘，外部可见，存在脏读风险） |
| **第三方系统支持** | ❌ 极差（要求第三方专门为你实现 Try 预留接口） | ✅ 极好（仅需第三方支持常规退款/取消 API，如微信支付） |
| **开发成本** | 🔴 极高（一个业务需写 Try/Confirm/Cancel 三个接口） | 🟡 中等（只需写正向 T 和逆向 C 接口） |
| **最佳适用场景** | 核心金融扣款、内部高并发资金/资产转换 | 长流程业务、跨企业/第三方系统的采购预订 |

## 📊 五、分布式事务方案选型决策表

| 维度 | 本地消息表 / 事务消息 | Saga 模式 | TCC 模式 | 2PC / XA 模式 |
| --- | --- | --- | --- | --- |
| **一致性级别** | 最终一致性 | 最终一致性 | 强一致性（预留资源） | 强一致性 |
| **隔离性** | 低 | 低（存在中间状态） | 高（资源隔离） | 极高（数据库强锁） |
| **性能/吞吐量** | 🚀 极高 | 🟢 高 | 🟡 中等 | 🔴 极低（强锁阻塞） |
| **代码侵入性** | 低 | 中（需写补偿接口） | 高（需写 T/C/C 三个接口） | 极低（框架完成） |
| **推荐使用场景** | 异步解耦、跨系统通知 | 长流程业务（电商/物流） | 核心金融扣款、资产转换 | 不推荐在微服务中使用 |

## 🎙️ 六、面试高分口答模板

> **问**："在微服务架构下，如何保证跨服务的原子性与数据一致性？"

**答**："在微服务架构中，由于数据库物理隔离，无法直接依靠单体数据库的 ACID 锁。我们遵循 BASE 理论，根据业务对一致性的要求强弱来选择不同方案：

1. **非实时强绑定的异步场景**（如：下单成功发积分/短信）：采用 **'本地消息表 / 事务消息（Outbox Pattern）'**。依靠本地数据库事务保证业务更新与消息写入的原子性，配合 MQ 的重试机制与消费端强幂等，做到异步最终一致性。

2. **金融级资金/资产扣减场景**（如：跨服务转账/扣款）：采用 **'TCC 模式'**。在应用层拆分为 Try（冻结预留资源）、Confirm（真正扣减）和 Cancel（解冻释放），通过资源隔离避免脏读。重点处理好空回滚、防悬挂与幂等性。

3. **复杂长流程业务**（如：供应链订单流转/接入第三方系统）：采用 **'Saga 补偿模式'**，每个服务执行本地事务，一旦中途失败，通过编排器反向触发逆向补偿 API（Cancel 操作）进行数据回滚。

4. **对于二阶段 C 操作失败的保障**：无论是 TCC 还是 Saga，C 阶段逻辑上只许成功不许失败。若发生网络或宕机异常，统一依靠**协调器自动重试 + C 接口强幂等 + 断点日志恢复 + 极限告警人工干预**来确保全局原子性。"
