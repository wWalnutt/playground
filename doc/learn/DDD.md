# 🧠 Domain-Driven Design (DDD) 核心通关笔记

## 🎯 一、 DDD 的核心本质

- **对抗软件系统的“熵增”：** 随着业务变得极度复杂，代码的退化不可避免。DDD 的核心目的就是防止系统退化为无人敢动的“大泥球（Big Ball of Mud）”。

- **模型同构：** 让技术人员的代码结构、设计模型，与业务专家（PO/产品）的商業思维模型**达成高度一致**。产品怎么想业务，代码就怎么写逻辑，真正实现“代码即文档”。


## 🌐 二、 战略设计（Strategic Design）—— 顶层大局观

战略设计解决的是**系统架构、微服务拆分边界**以及**企业研发资源的分配权重**。

### 1. 通用语言（Ubiquitous Language）

- **定义：** 团队（产品、开发、测试）在沟通和工程落地时统一使用的标准口径。

- **工程体现：** 拒绝在代码中进行“人工翻译”。业务上叫什么词，代码里的**类名、方法名、数据库字段名**就必须完全使用同个英文单词（如：账户余额耗尽，代码写成 `account.isBalanceExhausted()`，而非 `money <= 0`）。


### 2. 限界上下文（Bounded Context）

- **定义：** 领域模型的**语言和业务边界**。在这个边界内，所有业务名词的含义是唯一的。

- **工程体现：** **微服务拆分的核心技术依据**。例如“套餐（Product）”在“销售微服务”里只包含图文描述，在“计费微服务”里只包含价格税率，它们在物理上被拆分到不同的限界上下文中，老死不相往来，彻底解耦。


### 3. 三大子域（Subdomains）—— 资源分配矩阵

针对复杂的商业系统，DDD 帮企业把好钢用在刀刃上：

- **核心域（Core Domain）：** 公司的**赚钱命根子和护城河**（如运营商的动态计费引擎）。复杂度最高，利润最高，必须派最顶尖的精英自研，重度使用 TDD 死守质量。

- **支撑域（Supporting Domain）：** 必不可少但无法提供差异化竞争力的功能（如 SIM 卡仓储物流）。通常选择普通团队自研或外包。

- **通用域（Generic Domain）：** 全行业通用的标准功能（如统一认证中心、短信网关）。坚决不自研，直接买现成服务（AWS/SaaS）或套用开源框架。


## 💻 三、 战术设计（Tactical Design）—— 代码防屎指南

战术设计解决的是**微服务内部的代码编写规范**，提倡**充血模型**，杜绝 Service 层的面条代码。

### 1. 实体（Entity） vs 值对象（Value Object）

|**特性**|**实体 (Entity)**|**值对象 (Value Object)**|
|---|---|---|
|**唯一标识**|**拥有唯一的 ID**。只要 ID 相同，就是同一个实体。|**没有 ID**。只要属性值完全相同，就是同一个对象。|
|**状态可变性**|**可变的**。属性可以天天变，但主体身份不变。|**不可变的 (Immutable)**。如果想修改，只能整体替换。|
|**工程举例**|用户（User）、订单（Order）。|汇率金额（Money）、收货地址（Address）。|
|**Kotlin神器**|标准的 `class`。|天生适合用 `data class` 来编写。|

### 2. 聚合 与 聚合根（Aggregate & Aggregate Root）

- **定义：** 聚合是将紧密关联的实体和值对象打包成的一个“高内聚业务单元”。而聚合根就是这个单元里唯一的“话事人”。

- **硬核规则：** **外部服务绝对不允许绕过聚合根去直接修改内部的子对象**。例如：你想修改订单里的商品数量，必须调用 `order.changeItemQuantity()`。由聚合根（Order）在内存里死守业务红线，从而确保数据的一致性和并发安全。


### 3. 领域服务（Domain Service）

- **定义：** 当某项业务逻辑**不属于任何一个特定的实体**，或者是一个涉及多个聚合的无状态操作时（如：银行转账，既不属于转出账户，也不属于转入账户），应该抽象为一个独立的领域服务。


### 4. 仓储模式（Repository）

- **定义：** 面向**聚合根**的持久化抽象，应用了**依赖倒置原则**。

- **本质区别：** DAO/Mapper 是直接面向数据库表结构的；而 Repository 接口定义在领域层，它只关心聚合根的存取（如 `save(Order)`）。具体底层是用 MyBatis 拼 SQL 存 MySQL，还是用 SDK 存 AWS DynamoDB，那属于外层基础设施的实现细节，与核心业务彻底解耦。


### 5. 领域事件（Domain Event）

- **定义：** 业务发生重大状态变更时抛出的事件（如“订单已支付”）。

- **最佳实践：** 聚合根内部状态变更后生成领域事件，通过 **Kafka** 投递出去，下游微服务监听 Kafka 异步消费，实现分布式系统之间的**解耦与最终一致性**。


## 📊 四、 架构对比：四层架构 vs 传统 MVC

### 1. 标准 DDD 四层包结构布局

```
your-project-root
├── ui/                  --> 用户接口层：接收 HTTP 请求，RESTful 路由，DTO 转化
├── application/         --> 应用服务层：纯瘦子，不写核心业务，只负责流程编排、事务控制
├── domain/              --> 领域层（核心安全区）：充血模型（聚合根、实体、VO）、Repository接口
└── infrastructure/      --> 基础设施层：Repository具体实现（MyBatis/JPA）、MQ/Redis/AWS配置
```

### 2. 三大本质区别

1. **驱动方式：** 传统 MVC 是**数据驱动**（建表驱动），一切围绕数据库跑；DDD 是**领域驱动**，先设计核心业务行为，最后才考虑怎么存盘。

2. **模型胖瘦：** 传统 MVC 是**贫血模型**，实体是空壳，Service 是大胖子，塞满面条代码；DDD 是**充血模型**，核心逻辑收敛在对象自己体内，Service 只负责编排。

3. **依赖反转：** 传统 MVC 从上往下死死绑定底层数据库；DDD 的 Domain 层是纯净的，不依赖任何特定数据库框架和注解，数据库变成了随时可插拔的“插件”。


## 🔄 五、 真实项目落地五步法流程

1. **事件风暴（Event Storming）：** 跨角色团队围在大白板前，梳理全链路发生的“领域事件”，摸清业务全貌。

2. **提取通用语言：** 将模糊的业务词汇标准化，形成团队统一的英文业务词典。

3. **限界上下文划分：** 圈出语言和模型的边界，确定**微服务拆分蓝图**。

4. **梳理内部聚合：** 进到单个微服务内，找出**聚合根、实体和值对象**。

5. **充血编码交付：** 重度依赖 **TDD（测试驱动开发）** 编写纯净的领域层代码，快速迭代交付。


## 🎯 六、 架构师级别

> **谈本质：** “在我看来，DDD 的本质是在对抗大型复杂系统的熵增。它打破了技术与业务的物理隔离，让我们的代码结构和商业蓝图高度同构，从而赋予了团队持续进行敏捷交付的底气。”

> **谈战略：** “我们在项目启动阶段，会通过限界上下文为微服务划定金科玉律般的物理边界，确保服务间高内聚、低耦合。同时，把宝贵的自研精力 100% 聚焦在动态计费这类的‘核心域’上，而对于通用域则直接消费 AWS 现成的云服务，实现企业研发投入产出比（ROI）的最大化。”

> **谈战术：** “工程落地时，我们坚决抛弃导致面条代码的贫血模型，转而拥抱充血模型。核心逻辑收敛在聚合根内部以死守业务一致性红线。同时利用 Repository 模式应用依赖倒置原则，让底层的 MySQL 或 AWS 彻底降维成核心领域的‘外挂插件’，从而让核心业务代码具备极高的纯净度和可测试性。”
